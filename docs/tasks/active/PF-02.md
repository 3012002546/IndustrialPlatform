用户要求本次同时考虑后续页面，按“代码路由 → 权限/资源注册 → 菜单配置 → 发布加载”的既有机制收束，不是新增插件平台或代做其他 PF 页面。实施 05 第7.5/7.6节继续有效：服务/模块声明资源与权限，Identity 拥有目录和授权；远程清单注册端点默认禁用的边界不变。

- **代码与菜单分离**：页面组件随前端版本部署，以稳定 routeName、路由权限/终端/workspace、locale接入；后端只下发已声明的 routeName，不下发组件路径、任意URL/脚本，也不从数据库加载可执行代码。当前生产 routes.ts 大多静态 import，仅开发样板已有懒加载；本轮只给后续新页采用 `() => import(...)` 的接入范式和验证，不顺带全量改造既有路由/黄金页。
- **注册升级可持续**：现有 RegisterManifestAsync 在版本变化后对已有 ResourceNId/FeatureNId 一律拒绝复用，单独只报新增项又可能留下旧资源版本悬空。随本次一致性缺陷完善现有受信任模块升级用例：同模块、稳定资源身份与权限语义的既有声明可以幂等重申/更新其声明版本，新增资源增量登记，模块清单/资源/受信回执原子一致；跨模块占用、同版本异checksum、权限身份变化或遗漏仍在用资源不得静默接受。全部授权和校验继续在服务端，不启用远程注册、不改Identity目录写入边界、不设计平行注册框架。先在现有服务/种子机制中证明可复用；真正需要新的服务身份/跨模块协议时只记边界，不扩张实现。
- **新增页进入可配置资源，不自动改正式菜单**：已登记的 Active Page 应出现在菜单编辑的资源选择中；为区分“已登记但尚未配置菜单”可使用现有资源与草稿做小型派生筛选/状态，不增加一张登记表。管理员选择一级导航/目录，关联菜单后预览、校验、发布；模块升级保留用户的分组、父级、排序、标签和发布快照，特别是主题页移至服务与运维的修改。默认菜单导入只是内置模板，不冒称发现了所有新模块，也不得用更新前端静态默认菜单自动覆盖 configured=true 的租户快照。新模块模板扩展遵循当前声明来源和接入清单，不复制更多平行硬编码列表。
- **部署不同步明确降级**：当前 runtime/预览未检查 routeName 是否存在于当前前端构建。复用现有 Router 路由存在性检查或其只读注册名投影，在配置/预览提示“当前前端版本未包含此页面”，阻止本界面新发布明显无法加载的入口；运行时不生成抛错的 RouterLink，提供明确不可用/升级提示并保留其他正常入口，不静默复活整份默认菜单。客户端检查不是权限或全终端部署权威：服务端继续验证可信模块资源；若要服务端证明各终端部署版本，需要独立可信部署清单，该跨模块协议本轮不新建、不宣称已实现。
- **验收新增接入回归**：用测试模块/页面声明演示 v1→v2 新增页面且重申旧页面，真正SQL重载后资源/清单/回执一致；新增资源可选择放入已有目录并通过生产发布/runtime链，旧菜单仍在用户调整位置；同版重试零重复、错误归属/校验和不匹配拒绝、前端无该route时明确提示、后端先升级/前端先升级不导致整页导航崩溃、无权限仍403。测试页面只在隔离夹具/测试路由注册，不给产品混入占位业务页。新增页的文件入口/必要字段/部署顺序/维护约束以精简接入清单附在本轮 evidence，已有Schema/API能力不足之处诚实说明。
