## 数据与共享治理

- 七模块共用一个 PostgreSQL Schema `reference_data`、一个迁移/种子账本、一个 `reference_data.outbox_message` 和一个 `reference_data.cache_generation`。迁移按 001 baseline、002 Dictionary、003 Parameter、004 DynamicProperty、005 UnitOfMeasure、006 Metadata、007 CodingRule、008 StateMachine、009 shared、010 integrity、011 cache generation 顺序执行；010 清理重复 Dictionary Draft 后增加唯一索引，011 增加数据库权威缓存 token。
- 当前无入站事件消费者，因此没有 Inbox、Checkpoint 或七套模块级 Outbox。扫描未发现 `EnsureCreated` 或 CodeFirst 自动建表路径。
- 发布或配置变更、适用的 Outbox 行以及受影响的持久化 generation token 在同一数据库事务提交；事务回滚时 token 同步回滚。一个 Dispatcher 使用每批次 DI scope，重试间隔为 1、2、4、8、16、30、60、120、300 秒，第 10 次失败保留为 Failed。
- 七个 V1 routing key：
  - `industrial.reference-data.dictionary.published.v1`
  - `industrial.reference-data.configuration.changed.v1`
  - `industrial.reference-data.dynamic-configuration.published.v1`
  - `industrial.reference-data.metadata.published.v1`
  - `industrial.reference-data.coding-rule.published.v1`
  - `industrial.reference-data.state-machine.changed.v1`
  - `industrial.reference-data.unit-of-measure.changed.v1`
- Redis envelope 携带数据库权威 generation token；已有账本行使用随机 256 位值，缺行时使用基线 `0`。每次命中均以 PostgreSQL `reference_data.cache_generation` 的标量结果校验。无法验证或 token 不一致时按未命中处理，不返回无法证明有效的旧值。token 按 NId、AppDomain、来源/租户/current/Revision/list 等逻辑范围细分；Redis v3 物理值键和 generation 键使用同一 hash tag，满足 Redis Cluster Lua 同槽要求。约定 TTL：Dictionary 30 分钟，Parameter 5 分钟，Dynamic Schema 15 分钟、Records 5 分钟，Metadata/CodingRule 15 分钟，Unit/State current 5 分钟、固定 Revision 30 分钟；不存在结果不缓存。

## 降级与恢复

### Redis

单独停止任务 Redis 后，`referencedata.redis` capability 变为 Degraded；`referencedata.postgres` 与 `referencedata.initialization` 保持 Healthy。使用真实不可用 Redis 适配器和同一真实 PostgreSQL 行执行服务级 Cache Aside，1/1 通过，证明缓存失败后由数据库返回值且缓存写失败不会覆盖业务结果。Redis 恢复后 readiness/capability 回到 200/Healthy，并可重新写入上述缓存键。

另使用真实 Redis 与 SQLite 权威账本验证非对称故障：模拟写入副本仅在业务数据库事务更新 token、完全漏发 Redis 失效通知，另一缓存副本仍拒绝旧 envelope。独立事务测试证明 token 随业务事务提交或回滚；真实 PostgreSQL 专项还覆盖 011 建表及同一 key 连续写入的 `ON CONFLICT DO UPDATE` 路径。随机 token 避免数据库时间点恢复后的整数 generation ABA。

UnifiedHost 使用带 `sid` 的管理员会话时，Identity 的撤销检查按安全设计对 Redis fail-closed，因此共享 Redis 全停期间外部管理员请求在授权阶段返回 503；请求没有进入 ReferenceData 服务。此行为与 ReferenceData Cache Aside 回源分别记录，未把宿主安全依赖的 503 误记为 ReferenceData 数据层失败。

### RabbitMQ

单独停止 RabbitMQ 后，`referencedata.rabbitmq` capability 变为 Degraded，ReferenceData PostgreSQL/initializer 保持 Healthy。此时经真实认证创建并发布 `PF03_RABBIT_002208`，HTTP 为 201/200，Outbox 状态为 Pending、`attemptCount=0`。RabbitMQ 重启后 Dispatcher 自动补发，状态转为 Published、`attemptCount=0`，readiness/capability 恢复 200/Healthy。最终收口时 Outbox 汇总为 Published 16、Pending 0。

UnifiedHost 的整体 ready 在故障期间为 503，来源分别是既有 `identity.redis/systemdata.redis` 或 `systemdata.rabbitmq` 健康检查；ReferenceData 自身的 core checks 始终 Healthy，ReferenceData Redis/RabbitMQ 只出现在 capability profile。

## 真实验收发现并修复的问题

- PostgreSQL Outbox payload 由字符串写 JSONB 会失败；改为参数化 `CAST(@Payload AS jsonb)`，并保留 `traceId/scopeId/tenantNId` 等可空通用字段。
- PostgreSQL CodingRule UPSERT 中 `last_value` 与目标/EXCLUDED 列歧义；增加目标别名和限定列名。
- Hosted Outbox Dispatcher 曾直接持有 scoped store；改为每批次通过 `IServiceScopeFactory` 建立异步 scope。
- UnifiedHost health 契约测试仍按旧 profile 断言；更新为 core readiness 与 ReferenceData capability 分层。
- 补齐 DynamicProperty 已发布记录量和验证失败指标。
- Redis 失效通知在副本间发生非对称故障时可能遗留旧值；增加 `reference_data.cache_generation`，由业务事务原子写入随机 token，并在缓存命中和回填前以数据库 token 校验。
- 原模块级失效会扩大回源范围且 Redis Lua 多键操作可能跨 Cluster slot；token 改为按逻辑对象细分，物理键使用 v3 hash tag 保证同 slot。
- Dictionary 旧迁移可能遗留多个 Draft；010 在建立单 Draft 唯一索引前确定性禁用低修订重复项，并补齐克隆 CAS 与禁止旧修订反向发布。
- Outbox 多副本竞态可能把已确认消息覆盖成 Failed；终态更新改为受影响行判定，Publisher Confirm 获胜时 Published 保持最终状态。

以上修复均包含在最终 Release build、全解决方案测试、真实 PostgreSQL 专项与真实 Redis/RabbitMQ 验收中。
