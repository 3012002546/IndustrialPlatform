# 5. Entity设计规范

所有领域实体继承非泛型 `Entity`，主键统一为 `Guid`。SharedKernel 只定义实体语义，不引用 SqlSugar、PostgreSQL 或迁移属性。

```csharp
public abstract class Entity
{
    public Guid Id { get; protected set; }
    public bool IsFrozen { get; protected set; }
    public bool IsLocked { get; protected set; }
    public bool IsDeleted { get; protected set; }
    public string EntityType { get; protected set; }
    public DateTimeOffset CreatedOn { get; protected set; }
    public DateTimeOffset LastUpdatedOn { get; protected set; }
    public long OptimisticVersion { get; protected set; }
    public Guid ConcurrencyVersion { get; protected set; }
}
```

初始化约束：

- `IsFrozen`、`IsLocked`、`IsDeleted` 均为 `false`。
- 构造时只读取一次 `DateTimeOffset.UtcNow`，`CreatedOn` 与 `LastUpdatedOn` 使用同一个值。
- `EntityType` 为具体派生实体的完整类型名。
- `OptimisticVersion` 从 `0` 开始。
- `ConcurrencyVersion` 创建时生成非空 `Guid`。

统一行为：

- 派生实体修改字段前调用 `EnsureCanModify()`，完成修改后调用 `Touch()`。
- `Touch()` 更新 `LastUpdatedOn`、递增 `OptimisticVersion` 并刷新 `ConcurrencyVersion`。
- `Freeze/Unfreeze`、`Lock/Unlock`、`MarkDeleted/Restore` 是显式状态转换。
- 重复进入相同状态保持幂等，不推进版本。
- 已删除实体只能恢复；已锁定实体只能解锁；已冻结实体只能解冻。
- 非法状态转换抛出明确的 `BusinessException`。

仓储并发契约：

```csharp
Task UpdateAsync(
    TEntity entity,
    long expectedOptimisticVersion,
    Guid expectedConcurrencyVersion,
    CancellationToken cancellationToken = default);

Task DeleteAsync(
    TEntity entity,
    long expectedOptimisticVersion,
    Guid expectedConcurrencyVersion,
    CancellationToken cancellationToken = default);

Task RestoreAsync(
    TEntity entity,
    long expectedOptimisticVersion,
    Guid expectedConcurrencyVersion,
    CancellationToken cancellationToken = default);
```

Infrastructure 必须使用 `Id + IsDeleted + OptimisticVersion + ConcurrencyVersion` 执行原子条件更新。影响行数不是 `1` 时抛出专用并发异常。删除使用软删除 `UPDATE`，默认查询过滤 `IsDeleted = true`；通用仓储不提供物理删除。

业务实体示例：

```csharp
public sealed class WorkOrder : AggregateRoot
{
    public string OrderNo { get; private set; }

    public void Rename(string orderNo)
    {
        EnsureCanModify();
        OrderNo = orderNo;
        Touch();
    }
}
```

# 24. Health Check规范

所有服务必须区分 liveness 与 readiness。启用远程 PostgreSQL 的新服务只有在 SystemData 数据库编排 Operation 成功、逻辑身份与解析后的 `PhysicalDatabaseName` 一致且目标迁移版本匹配后才能 readiness Healthy；SystemData 不可用、迁移失败、目标身份不一致或目标数据库错误时必须 NotReady，并暴露脱敏 `OperationId`/TraceId 供诊断。

健康端点至少包括：

```
/health
```

返回：

```json
{
 status:"Healthy"
}
```

检测：

```
Database

Redis

RabbitMQ

```
