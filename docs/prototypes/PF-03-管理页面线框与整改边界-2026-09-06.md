日期：2026-09-06。状态：先行线框，作为本轮实现与真实页面验收基准；不代表已经实现。

## 本轮补充：舒适度与云端单库落地

用户后续反馈：页面仍拥挤，需更适合人工配置。下面的补充优先于早期线框中泛称“必要工具”的描述。

- 字典、动态属性、元数据、状态机、计量单位的左目录只保留搜索、必要筛选、刷新；参数上游两栏同样按查找/选中需求精简。编码规则是普通管理页，保留完整 AppDataTable 工具栏，不能被共享 compact 样式误伤。
- 舒适度不是把表格铺高或缩小字号：工作区外留白约 16–24px、区域内边距约 16px、标题和正文有层级，筛选与操作避免密集换行，名称可读，说明按需展开；按现有主题和密度适配，不创建第二套设计系统。
- 各区只显示当前任务相关动作；单项配置表单使用友好名称、简短帮助和明确保存/取消；错误信息靠近字段，提交中防重复，关闭或切换时保护未保存内容。技术术语只在用户确实需要时出现。
- 先更新对应线框和本地预览再落生产实现；验收以真实浏览器中目录、选中详情、空态和编辑弹窗四类场景的舒适度及操作完成情况为准。
- 云端存量修复已获用户明确授权：ReferenceData 独立库并入 Shared 目标，完成后删除该独立库。已核对本机私有配置为 Development / Shared / industrial_platform_dev / ServiceDatabases={}。此授权只针对核实后的 ReferenceData 独立库，不包括其他库或 Docker 数据卷。
- 数据库必须按 src/开发注意事项-数据库拓扑与本地配置.md 执行：先识别实际 PostgreSQL 实例、源库、目标库、数据/Schema/账本、活动连接及应用真实目标；备份源库和目标库并验证可恢复性，再制定并执行不覆盖既有目标业务数据的合并。源目标已有冲突不得猜测哪份正确，报告具体冲突。复制期间需一致性和防并发写入，不能静默停掉用户 IDE/宿主。
- 合并核对包括业务记录、ID、序列、约束、迁移/种子账本、实际读取路径。只有备份有效、数据核对通过、应用使用共享目标且源库不再被依赖时才清理精确旧库。不得 DROP FORCE、删除 volume 或重建 PostgreSQL。默认 postgres/template 系统库不算额外业务库。
- 同步云端私有 .env、部署脚本和下次创建容器时的拓扑输入；区分磁盘配置与当前容器环境，防止下一次启动重新生成旧库。记录最终物理库清单、共享库 reference_data 对象和实际连接证据，以及备份/恢复路径；凭据不进入输出、文档或 Git。
- 开发任务负责页面及获授权的云端修复；验收任务生产代码只读、云库只读，按稳定交接验证。两个任务完成后均保持未归档，模型配置不覆盖。

### 落地视觉基准

- 主从页的检索归属左侧目录：目录内保留一次业务检索、必要范围/状态筛选与刷新；不要再让相同检索条件占用右侧详情的首屏。目录卡片保留明确的“目录”语义和当前选中高亮。
- 右侧详情按“对象标题与状态 → 当前可执行动作 → 子项标题与新增动作 → 数据表”分组；标题区、操作区和表格之间使用约 16px 的稳定间距。对象的技术标识、范围、修订和状态放在辅助行，不与主名称竞争。
- 普通页编码规则不套用主从目录布局：页头操作、顶端查询和完整表格工具栏保持独立，表体继续占满剩余工作区。
- 视觉验收以真实已登录页面为准：在 1920 宽度下，目录、详情和分页均应完整可见；目录不出现导出、打印、分组、列设置、行设置或重复的第二套检索入口。

## 依据与共同规则

- 用户本轮给出的状态机线框和六页问题清单为直接依据。沿用会话《PF03前平台能力收束主任务》中 yefeng.club 的布局参考，以及 README 中 MalusAdmin 的后台视觉参考；实际实现使用现有管理组件、主题与用户管理黄金样板。
- 本轮真实 Chrome 页面显示：一级组和功能树仍为“参考数据”，元数据菜单仍为“元数据 Schema”；状态机左栏显示完整工具栏且多行折叠，左右区域仅占上半屏。需从真实导航来源、客户端缓存、当前宿主版本核对，不以代码字符串替换或 fixture 通过代替运行效果。
- 一级组及功能树统一显示“基础配置”，元数据显示“元数据定义”。保持服务名、API、权限 ID、数据库标识不变；保护用户自定义菜单，内置旧默认标题做窄范围兼容升级。
- “铺满”指工作区占满页签以下可用内容宽高，保留约 16px 外边距。左右边界齐平、底部齐平，工具区固定，各表体独立滚动，分页贴近各区域底部。空态也保持完整区域高度。不得以写死屏幕高度、扩大空白表格行或横向滚动实现。
- 常规两栏：左目录约 260–300px，右侧占余宽。参数三栏：约 220–260px、280–340px、其余宽度；按实际内容容器宽度适配。窄屏通过折叠上游目录/返回入口保持层级，不把三个模块挤成不可用细条。
- 目录只有名称、必要标识与状态，当前行背景高亮；无 radio/checkbox、无固定操作列占用目录宽度。目录标题旁新建，选中对象的编辑与更多放右侧上下文头。
- 目录工具仅搜索、需要的范围/状态筛选和刷新；每个工具只出现一次。目录不显示导出、打印、分组、全屏、列设置、行设置。通过现有 shared toolbar profile 实现，禁止 CSS 隐藏按钮。目录分页精简，不放页容量大下拉和跳页输入。
- 右区按业务需要显示查询和表格工具；不要每个小表默认堆满全部工具。创建按钮在对应区域标题行持续可见。权限不足/已发布只读时有明确状态说明；合法空集合也能新增。
- 页标题简短，减少长期占位的技术描述和重复标题；保留清晰字号层级、行距与留白。详情页签使用轻量下划线样式。
- 延续既有版本、聚合、权限、租户、并发语义；切换父对象清理子选择，防止陈旧请求覆盖与未保存内容丢失。

## 验收条件

1. 逐页对照上述线框，保存真实调试页面截图，覆盖当前窗口及 1366/1920 两种宽度；“无横向溢出”和“铺满剩余高度”是两条独立断言。
2. 真实菜单、功能树、页签、刷新后页面均显示新标题；核对已有数据库种子/运行时菜单及前端缓存的升级路径。保留自定义菜单文字。
3. 在可写测试父对象上验证各子区新增按钮（含空集合）、编辑/删除与刷新结果；明确测试数据的命名、权限与清理边界。已有业务记录不拿来做破坏性测试。
4. 参数三级表逐层切换，实际验证多值增删改查、默认/启停、必填与并发边界，不用 fixture 中存在按钮代替真实功能证据。
5. 原服务已由用户启动，保护 VS/VSCode/宿主进程。若后端升级需要用户调试宿主重新加载，记录准确阻塞，不用清缓存或 fixture 绕过后声称真实环境通过。
6. 开发自测后交给原验收任务；生产代码写入顺序交接。验收按本轮新增/修复范围验证，记录真实后端与 fixture 的区别。未满足任一核心条目不得给最终 PASS。
