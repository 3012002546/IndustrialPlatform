## 二、已经确认的方向

1. **使用 X6＋现有 Vue 3 / TypeScript / .NET / Studio。** 借鉴 ComfyUI 的节点、端口、拖线、选择、缩放和属性联动，不复制其代码、资产、Python 插件或执行队列。

2. **建设可复用的公共图形工作台。** 追溯是第一个消费者，后续生产流程定义、运行监视、任务步骤复用同一公共能力。公共图形组件不能依赖追溯实体或拥有生产业务状态。

3. **保留三个不同层次。** 领域定义表达对象、关系、活动、条件和参数等业务语义；显示布局表达节点位置、尺寸、端口呈现、折点和视口；运行投影表达实际对象、证据、执行实例、状态和时间。运行刷新不能修改定义或污染设计撤销历史。

4. **追溯查询与生产执行各自拥有领域语义。** 追溯允许环、多父和同端点多重证据边；画线不生成实际消耗。生产流程的持久化等待、任务推进、并行汇合、重试、返工和设备动作不由 X6 自动提供，也不属于 G1 的实现范围。

5. **复用现有 Studio 资源、草稿、不可变发布修订、权限和编辑外壳。** 不新建任意对象数据库、通用执行引擎、第二套 Scheduler 或插件市场；不为了复用立即拆 npm 包。

6. **已确认顺序：** 公共合同细化 G1 → 同一组件的追溯＋生产双领域独立 PoC G2 → 原 PF09-011～014 → 后续生产模块接入。

目前已有架构文档，不等于公共接口、X6 准入、PoC 或追溯功能已经完成。先核对最新源码，若已有后续进展，应保留并准确更新状态。

## 三、本次 G1 要完成的范围

目标：让下一会话可以按明确合同开展 G2，避免开发者自行猜测公共层和领域层分别保存什么、调用什么。

### 1. 核对现有可复用实现

只读检查 StudioEditorShell、共享 model/history、资源与发布、授权和应用端口等相关代码。记录真实文件路径、已有能力、耦合点和最小适配位置。历史架构中的“已有/缺失”判断必须与当前代码核对，不凭旧结论安排重写。

### 2. 细化最小公共图形合同

用文档内 TypeScript/JSON 示例和字段表明确：

- 定义投影、节点、端口、边与稳定身份。
- 领域定义、布局和运行投影的归属及引用关系。
- 节点目录、属性面板与连接规则的领域扩展方式。
- 编辑命令、连接校验、完整定义校验和诊断定位。
- 选择、只读模式、视口、加载与销毁。
- 运行快照、版本/代次、完整性和实例详情。

每项写清类型、必填/空值、默认行为、错误语义与版本兼容。只定义 G2 和追溯接入实际需要的公共能力，不建设覆盖所有业务的万能图模型。

### 3. 确定编辑事务、撤销和缩放合同

明确图形与属性的复合操作如何形成一次原子编辑；删除节点如何一起处理关联关系、布局和诊断；选择、缩放、运行刷新是否产生脏状态或历史；保存失败和并发冲突如何保留草稿；Studio 与 X6 如何保持单一权威历史、单一视口控制。

能从现有代码确定的直接给出建议；必须通过 X6 实测才能决定的内部接法，列为 G2 验证项，不能写成已验证。

### 4. 细化 TraceModel 适配映射

保留已有 objects / relations / layout / limits 及身份、授权和查询合同。逐项说明哪些字段直接复用，哪些只是前端投影，哪些确实需要兼容扩展及原因，哪些不应进入公共层。

不得把 X6 原始序列化 JSON 直接作为后端领域执行协议。涉及真实合同变化时，同步权威规格，避免两份文档维护不同 schema。

### 5. 细化运行投影和页面生命周期

明确模型修订、查询代次、响应版本、对象/证据身份与投影的匹配关系。覆盖旧查询/旧选择迟到响应、切模型/租户、取消、页面卸载、订阅和图实例释放。

追溯 Partial/Unknown 保持原语义，不强行套成任务 Running/Completed。生产示例中一个定义节点对应多个迭代/尝试时，汇总显示不能覆盖实例历史。

### 6. 给出最小页面结构和操作归属

设计、预览、运行三种模式分别说明工具栏、左侧目录或起点、中央画布、右侧属性或详情、诊断区。说明各模式可编辑内容、只读行为、保存/发布和领域操作入口。复用现有外壳，明确必要的窄适配，不重做看板、报表或低代码设计器。

### 7. 用两个纸面样例检查合同

- 追溯：多父、同端点多证据边和环，验证保存、投影、选中、诊断与证据详情。
- 生产：领料→称量→并行加工/检验→汇合→放行，检验有两次迭代，验证定义与多实例覆盖显示。

提供足够具体的数据示例及预期操作结果。生产状态由夹具提供，只验证公共合同能承载，不设计或实现真实推进引擎。

### 8. 整理 G2 的直接输入

交付公共合同及 schema/兼容策略、现有代码复用和最小变更位置清单、两个领域适配示例与固定夹具、单一历史/视口方案及待实测选择，以及 X6 版本、插件、许可、交互、性能和释放的核验清单。

分别列出已确定、待 PoC、后续生产三个状态清单。沿用已有 GX 与 A/B/D 验收映射，不另建一套 PF 编号。

## 四、必须保留的边界

- 完整对象身份，不合并不同工厂的同编码对象。
- 正反向查询显式映射；反向查找不颠倒真实业务箭头。
- 多重证据边和真实环保留；去重只阻止重复展开。
- Genealogy 与设备/质量 Context 分开。
- 追溯预算、凭证有效期和消费时授权沿最新权威合同。
- 单装追溯不要求安装 Report、Office 或生产模块。
- 当前页详情/文件/外链遵守授权、扫描与嵌入策略，不绕过 CSP。
- 不将报表“无固定预览有效期”套用到追溯凭证。
- 不改变报表、临时查询表格、Workbook 的既有生命周期。
- 保留现有 WIP 和用户运行环境，不顺手清理或重启。

## 五、落文档及完成标准

优先在已有的 [Studio 公共图形工作台与流程复用架构](Studio-公共图形工作台与流程复用架构.md)中细化。只有涉及权威字段/API/生命周期/验收变化时，才同步对应规格。在会话总览中更新 G1 的完成范围和 G2 入口。

内容确实过长时可以拆出一份明确被主文引用的合同明细，但不要复制出多份相互竞争的设计源。

完成前检查：

- 两个纸面样例能否消费同一公共合同。
- 是否存在公共图层直接依赖领域实体或执行业务查询。
- 每项操作、数据归属和失败行为是否明确。
- 是否保留已有追溯身份、证据、预算与授权语义。
- 需要 PoC 才能判断的内容是否明确标为待验证。
- 文档引用、字段、示例和任务映射是否一致。

最终报告：本次明确了哪些合同与复用方式、更新了哪些文档、哪些问题留给 G2 实测、下一会话可以直接开展的具体范围。

直接开展只读核对与文档细化，不再询问已经确认的技术方向；仅在歧义会实质改变业务语义或数据合同、且现有资料无法消除时提出问题。

## 六、模型强度建议

建议从 **High（高）** 开始。这是针对 G1 范围的工程判断：需要核对多份规格与现有源码，细化身份、版本、编辑事务和领域边界，但技术路线已明确，且没有产品实现或完整执行引擎设计。

如果出现多处相互冲突的合同、复杂状态语义需要集中推演，可以由用户将该轮调整为 **XHigh（超高）**；不建议一开始默认使用 Max/Ultra。具体可选档位以所选模型和客户端显示为准，这不是对任一档位效果的实测保证。

模型与强度由用户在新会话选择；本文件不要求智能体切换模型或覆盖用户设置。官方说明将推理强度作为推理投入与耗时等因素的取舍，参见 [OpenAI 推理模型说明](https://developers.openai.com/api/docs/guides/reasoning)。
