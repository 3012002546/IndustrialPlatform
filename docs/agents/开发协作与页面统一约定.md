## 2. 协作方式与执行边界

- 派发先描述用户可见的完整结果，再写实现边界；涉及双方或多端交互时，分别列明各方操作、可见状态、实际生效条件及结束后的界面与资源状态。只有接口成功、按钮可点或状态流转，不能替代实际业务效果。用户指出理解偏差时，由执行者简短复述后继续，不新增审批门；主控把确定的边界修订写回同一工作包，避免只留在零散消息里。
- 派发用一个紧凑执行合同写清：谁在何处执行什么动作→谁看到什么结果、影响哪项能力及生命周期、允许修改位置、已通过且保留的行为、最小验证步骤与完成边界。仅引用长方案不等于已经传达本次目标。执行者开工首条用一两句话复述用户可见结果后直接执行，不等待确认；复述出现偏差由主控立即纠正，不能等实现后才对齐。
- 易歧义名词和动作必须明确对象、呈现位置、影响范围及生命周期；参考图须说明借鉴的是布局、交互还是技术行为。用户补充要求同步覆盖当前合同，历史替代方案不得继续作为实现依据。领域内的具体取值写入对应任务，不能成为后续所有任务的默认功能。
- 交接分别标明代码回归、接口/信令、真实业务效果的证据，以及具体未测步骤；开发、验收和主控均不得把某一层PASS扩大为其他层已完成。不能为获得局部PASS不断缩小用户原定交付目标，也不因真实条件缺失反复跑已经通过的底层测试。
- **主控**负责范围、依赖、工作线、冲突、真正阻塞和最终结论；小修可在当前会话直接完成。大范围实现交开发，独立验收负责核验，不并写生产源码。
- **开发**负责连续实现、自测、真实最小业务链和返修；不能把独立验收当首次联调。内部TASK按依赖连续推进，不逐卡等待派遣、验收或提交。
- **独立验收**拿到稳定交付后检查完整约定范围，一次汇总可独立检查的问题，直接与开发交互；前置失败导致未到达的步骤如实记录，不绕过前置校验。
- 当前工作有可复用的开发/验收任务时复用，不重复创建。模型及推理强度按用户当次设置；**创建后所有续派、返修、交接均不传model/thinking，不恢复或覆盖用户后来调整的强度**。新任务核对实际指派，不自动升级模型。
- 一份源码同时只有一个写入者。稳定交接记录HEAD、既有WIP、改动清单及hash；无需为了交接强制提交。验收期间保持该快照稳定，避免共用bin/obj、测试数据库的并行写入。
- 常规已授权操作直接执行，开发与验收自行交接，不让用户传话。主控只接收里程碑、真实阻塞及最终结果，不持续轮询或转发每条进度。
- 同一问题两轮没有新证据，主控再判别环境、需求或能力原因；不能每轮盲目重测或换模型。重大越界、破坏性操作和实际工具审批单独处理，继续可安全完成的部分。
- 保留用户正在运行的IDE、调试及云Docker。优先复用实际实例，先查进程、端口和加载配置；不得假设Gateway或独立服务已运行，也不得擅自重启用户调试、改远端生命周期。
- 按当前任务已指派工作线执行；某次任务获准在主工作树develop开发，不代表后续任务自动继承该例外。保留无关改动，不擅自清理工作树、提交或推送。

## 3. 黄金页面与统一布局

黄金样板为 [IdentityUsersPage.vue](../../src/frontend/src/pages/pc/identity/IdentityUsersPage.vue)。统一的是页面结构、操作位置、交互和视觉，不机械复制用户管理的业务字段、权限、批量操作或流程。`yefeng.club`只作为已参考的信息结构，不复制其路由、权限或实现。

- 查询复用 `AppQueryPanel`，表格复用 `AppDataTable.vue/.ts`，结构化新增/编辑/详情/分配复用 `AppFormDrawer`，权限复用 `PermissionGate`；同时使用语言资源和主题变量。
- 标题、说明、数量、主操作只在合适位置出现一次。减少嵌套卡片、重复工具栏和过大空白，让业务区占满可用宽高；多个数据集仍保留可辨认的上下文标题。
- 查询标签与占位完全重复时可简化可见标签，但保留本地化可访问名称；正式表单、含糊字段、单位/帮助/校验不能因此丢掉标签。顶部查询与表头查询语义一致。
- 单条操作放行内，溢出操作收进“更多”；批量或当前上下文操作放对应业务区，优先 `toolbar-actions`。业务操作不混入列设置、排序、分组、打印等表格工具区。
- 结构化业务弹窗保留共享的居中弹窗/右侧抽屉偏好。删除、启停等单纯决策仍用确认框；不能为统一样式改变业务验证或一次性安全结果的展示。
- 深色主题背景上的按钮使用可读浅色文字；检查明暗主题、两种语言、焦点、键盘、空态、加载与错误态，不用写死颜色修一处破坏另一处。
- 纯样式调整不得顺手改变API参数、查询范围、权限、校验、路由、事件和保存结果。公共组件更改必须验证受影响旧页面，尤其用户管理查询。

## 4. 行选择、主从和响应式

- 普通CRUD默认不选行；确实需要一个上下文时单选；真正存在批量操作才多选。使用稳定业务row-key，过滤、分页、租户或父级变化后按业务清理或核对选择。
- 当前 `AppDataTable` 已有 `row-click`、`activeRowKey`、`selectedRowKey` 和 `selection-change`；历史参考中“没有row-click”已不适用。行点击、高亮与业务选中是不同契约，不能互相假定；跨页保留选择须有明确支持和验证。
- 主从布局左侧紧凑、右侧主业务区更大；左侧保持挂载，详情局部加载。旧异步响应或错误不得覆盖新选择，无父级时清空右侧并禁用依赖操作，禁止退化为无范围查询。
- 树形配置适合比较和行配置时使用全宽树表，预览/历史通过明确入口展开；不挤入三个完整工具栏。小列表用精简工具集，不通过私有DOM或CSS硬藏公共能力。
- 非平凡布局先用现有线框图核对区域、选中上下文、主操作和加载归属；小修不另造设计流程。弹窗、表格和详情区按职责滚动，操作区可见，悬停显示滚动条时避免宽度跳动。
- 收起必须有持续可见的重新展开入口；切换布局保留合理的选择、草稿与状态。提交有同步防重入和busy状态，不能只依赖遮罩；失败保留表单，409按并发提示重新读取/比较。

## 5. 需求调整与经验归纳

- 主控负责把用户修正同步到当前执行合同、权威规格与状态入口；开发和验收消费同一版本。不能只转发一句“按新要求调整”，也不能只要求执行者“仔细理解”而不消除冲突描述。
- 调整范围时写清改变的结果、保留的已通过行为、受影响文件与最小复验范围。局部修复不顺带重做整套交互；涉及数据、授权或公共契约则明确扩大检查的原因。
- 记录教训使用“现象→原因证据→通用预防动作→适用边界”。具体业务按钮、数据字段、特殊权限及功能完成状态回写领域文档，不能复制进通用约定。
- 已确认的验证结果按范围和版本保留；服务端状态不等于前端呈现，涉及异步刷新、事件或轮询时检查实际用户反馈。工具临时不可用不撤销已有结果。
- 新阶段分别判断上阶段交付是否可用、本阶段输入是否齐备。用户明确后置的验收不自动阻塞下一阶段；但目标设备、外部契约、签名发布等影响实现的未知输入必须先核验，不让执行者自由猜测。

## 6. 菜单、服务、数据库与唯一配置入口

- 功能可发现必须闭合：命名路由 → API/控制器注册 → 权限目录与策略 → 导航种子/增量版本 → 当前租户和登录人的动态菜单 → 本地化 → 实际打开。只有导航TS或页面文件不算完成。
- PC/PDA/Mobile分别核对菜单及终端能力。既有库不会自动重放已登记种子，新增版本时保留用户自定义；不能仅改种子内容后期待旧库自动出现入口。
- UnifiedHost沿现有模块目录接入服务、控制器、初始化、健康检查和端点，避免Program逐个堆注册，也不做不受控全程序集扫描或重复路由注册。
- **开发私有配置只维护 `src/backend/appsettings.Development.local.json` 一份**，正常开发宿主共用；同目录example仅为模板，不是第二运行配置源。禁止在多个Host重复填写同一开关或凭据。
- 物理库选择以 `DatabaseTopology` 为准：Shared与PerService分别验证，云Docker不会自动读取应用JSON。私有JSON的实际覆盖顺序按数据库文档执行，不假设环境变量总是最后生效；隔离SQLite模式按明确入口跳过私有基础设施。
- 不输出或提交私有配置、账号、密钥。变更配置或代码后，区分文件已修改与运行进程已加载；不替用户擅自重启正在调试的实例。
- 已应用迁移只追加新ID，不重写checksum，不删除账本或清库压掉错误。Inspect保持只读并处理旧账本结构；验证新库、既有库升级、幂等二次启动及旧功能。
- 表、实体与字段必须有面向人工接手的中文说明，写清“一行代表什么”、字段含义/来源/修改时机、类型约束、空值/默认、关系及维护限制；源码注释、数据库说明与详细字典同步，不能只翻译字段名。具体格式和交付检查沿[共同派遣标准§3.1](../implementation/STANDARD-派遣前详细设计与页面验收.md#31-面向人工接手的表实体与字段说明)，按本次实际范围补齐，不改写历史迁移或扩成无关全仓整理。
- 截止时间实际落库后验证UTC round-trip；单provider修复不能破坏其他provider语义。不同用途的业务版本和乐观并发版本分清，不能用延长超时或手改业务状态代替修复。
- 开发环境的临时放行必须有明确适用范围和恢复验证条件，配置细节及阶段安排记录在所属文档。跳过外部依赖不等于真实依赖通过，也不能取消无关授权和数据约束；Git分支名称不决定实际运行环境。

## 7. 验证怎样做，怎样避免反复返工

| 阶段 | 应完成的检查 |
| --- | --- |
| 开工一次对齐 | 核对实际代码/契约、工作树WIP、运行入口、配置、允许测试数据、浏览器和外部依赖；不靠历史端口、mock或文档猜实际环境 |
| 开发过程中 | 从真实初始状态跑通最小纵向链，真实发送端与接收端一起验证；失败修根因并继续验证上下游，不由fixture提前填完授权/绑定/审批 |
| 稳定交验 | 独立验收完整约定范围，交付快照、场景结果、环境和证据，不只报测试数量；实现、自测、独立验收分开标注 |
| 返修 | 复验缺陷、改动和受影响路径；公共组件、权限、跨模块契约、数据一致性或发布门禁需要时才扩大回归 |
| 最终交付 | 主控核对结论、证据、范围及限制，按仓库要求完成最终Release编译；不第三次机械重复相同全套测试 |

源码变化后先新鲜Release构建再运行 `--no-build` 测试；正常后端门禁为 `dotnet build src/backend/IndustrialPlatform.slnx --configuration Release` 后接 `dotnet test src/backend/IndustrialPlatform.slnx --configuration Release --no-build`。读取退出码及通过/失败/跳过数，编译锁解除后重建；旧产物和跳过不能算通过。小修按影响做定向验证，文档整理不运行业务全套测试。

前端单文件定向测试使用明确的 `pnpm exec vitest run <测试文件>`；不要把 `pnpm test:unit -- <测试文件>` 默认当作过滤已生效。执行前核对实际脚本和参数，执行中核对选中文件范围，发现意外全量及时停止；若已跑完，如实记录范围偏差，不为纠正记录再跑一次，也不让验收或主控重复同一命令。

真实UI检查覆盖HMR是否加载、控制台/网络、菜单可达、响应式和关键动作；构建成功不等于页面运行成功。用隔离账号/租户/测试数据，清理只针对本轮自有资源，不破坏用户数据与调试。工具不可达、依赖缺失、已证实缺陷、用户暂缓分开记录；替身/协议模拟不等于真实外部服务验收。

- 定位先找最早失败环节：入口/前置条件→接口或事件→处理/持久化→呈现。每轮记录预期、实际、证据及被排除的假设；先确认流程在哪一步失败，再改对应实现。不能用反复改UI文案掩盖底层失败，也不能因工具连接失败就重启用户服务或重查已确定环境。
- 异步修复同时核对迟到成功、迟到失败与无上下文fallback。回包须归属原操作、版本及能力；旧错误不覆盖新状态，成功只清对应来源，不能全局吞错。测试要制造真实触发顺序：例如延迟回包、原生DOM尺寸与响应式状态不一致，不能先把mock改成修复所期待的状态。
- 相同症状的已知独立原因应在一次交接集中列出；返修后验证失败点及直接上下游。开发自测、验收只读与用户实测各自记录，不以测试数量、正则断言或模拟PASS扩大为真实业务PASS。
- 用户确认通过的场景及时关闭；用户明确延期的场景登记目标阶段、触发条件和届时范围，不继续列为当前返工阻断，也不未经安排启动验证。当前状态只列有效问题，过时FAIL/MISSING放历史并标明被哪条结论覆盖；原始证据不追溯改写。

提交仅在适用授权与交付流程内执行：精确范围，检查tracked/untracked/ignored/staged/unstaged，排除bin、obj、TestResults、dist、缓存、日志和秘密；CLAUDE.md未明确要求不暂存。推送不强推，失败定位实际Git传输链路，成功核对远端hash及ahead/behind为0/0，不把保留WIP的工作树称为干净。

## 8. 持续更新与适用范围
