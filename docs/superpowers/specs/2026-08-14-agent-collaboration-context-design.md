# Industrial Platform 多智能体协作与上下文治理设计

## 1. 目标

在保留详细蓝图、实施方案和验收证据的前提下，降低 Codex、Claude Code、Harness 重复读取全量文档造成的 token 消耗，并保证并行开发可隔离、可追踪、可验收。

本设计只治理智能体角色、工作树、记忆文件、任务派遣和结果回写，不改变业务架构与既有实施方案。

## 2. 已确认决策

1. Codex 是项目总负责人，也是架构、蓝图、TODO、优先级、任务派遣和最终验收的唯一决策入口。
2. Claude Code 与 Harness 都是编码执行智能体，职责等价，不自行改变总体蓝图、优先级或其他任务范围。
3. 两个编码智能体允许并行工作，但必须使用独立 Git worktree 和独立任务分支。
4. 禁止两个编码智能体在主工作目录或同一工作树内同时编码。
5. 详细实施文档继续作为权威资料，但编码智能体只读取任务卡明确引用的章节。
6. 记忆文件只保存稳定规则和上下文路由，不再累积会话快照、历史测试数字和完整模块百科。

## 3. 角色模型

### 3.1 Codex：总负责人

Codex 负责：

- 维护项目蓝图、阶段计划和开发 TODO；
- 分析任务依赖、公共文件冲突和可并行性；
- 创建任务卡并指定执行者、worktree、分支和允许修改范围；
- 审查编码智能体提交的代码、验证证据和剩余风险；
- 按依赖顺序集成提交；
- 在集成结果上执行最终 Release 构建和全量测试；
- 维护当前状态、任务归档和最终验收结论。

Codex 不把未经裁剪的完整历史上下文复制给编码智能体。

### 3.2 Claude Code：编码执行智能体

Claude Code 负责：

- 在被分配的独立 worktree 和任务分支内工作；
- 按任务卡和指定设计章节实现代码；
- 执行定向构建、测试和必要验证；
- 提交仅属于本任务的变更；
- 回写结构化任务证据。

Claude Code 不负责选择下一任务、修改总体蓝图、更新全局状态、集成其他分支或推送总体进度。

### 3.3 Harness：编码执行智能体

Harness 与 Claude Code 职责等价，使用相同执行协议，但读取 `DSH.md` 作为入口。Harness 不读取或维护 Claude Code 的会话历史。

## 4. Git 并行隔离

### 4.1 工作区布局

```text
IndustrialPlatform/                 主工作树，Codex 总控与最终集成
IndustrialPlatform-worktrees/
  pf-00/                            Harness 工作树
  pf-02/                            Claude Code 工作树
```

示例分支：

```text
develop                             Codex 集成基线
task/pf-00                          Harness
task/pf-02                          Claude Code
```

### 4.2 隔离规则

- 一个活跃任务对应一个 worktree、一个分支和一个负责人；
- 同一文件原则上不分配给两个并行任务；
- 无法避免公共文件重叠时，由 Codex 确定先后顺序，不并行修改该文件；
- 编码智能体不得在主工作树提交；
- 编码智能体不得合并、rebase、cherry-pick 或推送其他任务；
- Codex 验收后在主工作树完成集成；
- 集成冲突由 Codex 处理，必要时退回原执行者修正。

## 5. 文档与记忆分层

```text
AGENTS.md                         Codex 总控入口与稳定治理规则
CLAUDE.md                        Claude Code 极薄入口
DSH.md                           Harness 极薄入口
docs/agents/EXECUTOR.md          两个编码智能体共用执行协议
docs/status/CURRENT.md           当前项目状态，仅 Codex 维护
docs/tasks/active/               活跃任务卡
docs/tasks/archive/              已完成任务卡
docs/evidence/                   任务验证与验收证据
docs/implementation/             完整蓝图和实施方案
docs/decisions/                  稳定架构决策记录
```

### 5.1 `AGENTS.md`

建议不超过 10 KB，保存：

- Codex 总负责人身份；
- 三类智能体的职责边界；
- worktree、分支、派遣、验收和集成规则；
- 文档加载顺序；
- 仓库构建、测试、提交和推送硬约束；
- 当前状态文件与任务目录入口。

不得保存完整模块进度、历史测试数字、会话快照或大段业务设计。

### 5.2 `CLAUDE.md` 与 `DSH.md`

两个文件建议各不超过 5 KB，只保存：

- 当前智能体身份；
- 必须读取 `docs/agents/EXECUTOR.md`；
- 只能执行 Codex 指派的任务卡；
- 只能读取任务卡明确列出的设计章节；
- 禁止修改全局状态、总体蓝图和其他任务；
- 禁止在主工作树编码；
- 交付结果必须写入任务 evidence。

两者不保存当前进度和历史踩坑。稳定公共规则只在 `EXECUTOR.md` 维护一次。

### 5.3 `CURRENT.md`

由 Codex 独占维护，只记录：

- 当前集成基线；
- 进行中任务、负责人、分支和依赖；
- 待派遣任务；
- 当前阻塞项；
- 最近完成任务及 evidence 链接。

任务结束即从进行中列表移除，历史进入 archive/evidence，避免文件无限增长。

## 6. 任务派遣协议

每个任务卡必须包含以下字段：

```text
任务编号
状态
负责人
目标
输入文档与精确章节
依赖
worktree 与分支
允许修改范围
禁止修改范围
预期输出
定向验证命令
验收标准
结果回写位置
建议提交信息
```

任务卡必须明确写出“无需读取”的文档范围，禁止使用“阅读全部项目文档”作为输入要求。

## 7. 执行与交付流程

```text
Codex 更新蓝图/TODO
  → 判断任务依赖与文件重叠
  → 创建独立 worktree/分支
  → 生成任务卡并派遣
  → 编码智能体读取薄入口、执行协议、任务卡和指定章节
  → 编码、定向验证、提交
  → 写入 evidence 并返回 commit hash
  → Codex 审查 diff 与证据
  → Codex 集成
  → Release 全量门禁
  → 更新 CURRENT 与归档任务
```

编码智能体的最终回报固定为：

```text
状态
提交哈希
修改文件
关键决策
验证命令与结果
剩余风险
```

禁止在回报中复述完整实施方案。

## 8. 测试职责

- 编码智能体执行与任务直接相关的定向构建和测试；
- 源码发生变化后不得用陈旧的 `--no-build` 结果代替新构建；
- Codex 集成后执行仓库规定的 Release build 和全量 test；
- 并行任务不得共享同一 `bin/obj` 输出目录；worktree 天然提供该隔离；
- 全量验证只在集成阶段集中执行一次，避免每个执行者重复消耗时间和 token。

## 9. 文件所有权

| 内容 | 唯一维护者 |
| --- | --- |
| `AGENTS.md` | Codex |
| `CURRENT.md` | Codex |
| 蓝图、TODO、依赖和优先级 | Codex |
| 任务卡初始内容 | Codex |
| `CLAUDE.md`、`DSH.md`、`EXECUTOR.md` | Codex 制定，编码智能体只读 |
| 任务代码 | 被指派的编码智能体 |
| 任务 evidence | 被指派的编码智能体 |
| 最终验收与任务归档 | Codex |

## 10. 失败与冲突处理

- 任务范围不清：编码智能体停止扩张范围，在 evidence 中记录并请求 Codex 决策；
- 发现公共文件冲突：不自行合并，返回 Codex 重新排序；
- 定向测试失败：执行者保留失败证据并修复本任务问题；
- 全量测试在集成后失败：Codex 定位归属并退回对应任务；
- 任务被中止：保留 worktree、分支和现有提交，Codex 决定恢复或废弃；
- 任何智能体都不得通过清理其他工作树、强制重置或覆盖未提交内容解决冲突。

## 11. 迁移策略

迁移按以下顺序进行：

1. 保存现有 `CLAUDE.md` 与 `DSH.md` 中仍有效的信息；
2. 将稳定公共执行规则归并到 `docs/agents/EXECUTOR.md`；
3. 将当前进度提炼到 `docs/status/CURRENT.md`；
4. 将长期技术决策保留在实施方案或独立 ADR；
5. 将历史会话快照和测试证据移入 archive/evidence；
6. 将 `CLAUDE.md`、`DSH.md` 重写为极薄入口；
7. 新建 Codex 使用的 `AGENTS.md`；
8. 建立 active/archive/evidence 目录和任务模板；
9. 验证三类入口之间没有职责冲突、重复规则或失效链接；
10. 后续新任务一律通过独立 worktree 派遣。

## 12. 成功标准

- Codex、Claude Code、Harness 的职责无重叠决策权；
- 两个编码智能体能够在独立 worktree 并行执行；
- 任一编码智能体启动时不需要读取完整项目历史；
- `CLAUDE.md` 与 `DSH.md` 均为轻量入口；
- 当前状态、详细设计、历史证据各有唯一存放位置；
- 每个任务能从任务卡追踪到分支、提交、验证证据和最终验收；
- 集成门禁由 Codex 统一执行，结果可以证明而非推测。
