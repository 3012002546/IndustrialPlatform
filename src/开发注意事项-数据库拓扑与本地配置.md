# 开发注意事项：Development 本地配置与数据库拓扑

## 1. 目的与强制原则

本文约束 `src/backend/appsettings.Development.local.json`、各后端宿主和云端开发 Docker 的数据库配置方式。后续新增服务、模块或初始化流程时，必须按本文同时验证 `Shared`（单物理库）和 `PerService`（按服务分库），不能只验证当前开发环境能启动。

必须遵守以下原则：

1. `DatabaseTopology` 是物理数据库选择的唯一权威来源。业务服务不得从服务名、逻辑库名、程序集名或连接串默认值自行推导物理库。
2. `RemoteDevelopment.PostgreSql` 只提供服务器和凭据，不配置数据库名；数据库名必须由 `DatabaseTopology` 解析。
3. `Shared` 只允许用于 `Development`。当前 Identity、SystemData、ReferenceData 以及以后接入的服务都连接同一个物理库，但仍保持各自的 Schema/表、Repository、Migration/Seed Ledger、Outbox 和数据所有权。
4. `PerService` 必须为当前启动宿主提供显式映射。缺少映射必须启动失败，禁止静默回退或自动创建 `<service-name>` 数据库。
5. “单进程”不等于“单库”，“多进程”也不必然等于“多库”。进程部署由 UnifiedHost/Gateway 决定，物理库拓扑只由 `DatabaseTopology.Mode` 决定。
6. 应用配置只决定应用连接目标，Docker 配置决定实际预创建哪些数据库；两侧必须人工保持一致，不能假设 `appsettings.Development.local.json` 会自动传入云端 Docker。
7. 拓扑切换只改变目标解析，不自动复制、合并或删除数据。已有环境切换前必须另做经过审批的数据迁移方案。

## 2. 文件位置、加载方式与安全边界

- 模板：`src/backend/appsettings.Development.local.example.json`
- 本机私有配置：`src/backend/appsettings.Development.local.json`
- 云端基础设施私有配置：`deploy/cloud-dev/.env`

两个私有文件均已被 Git 忽略。不得提交、截图、粘贴或在日志中输出真实主机、账号、密码、API Key、完整连接字符串和其他凭据。

Development 宿主通过 `AddOptionalLocalDevelopmentInfrastructure(...)` 从项目内容根目录向上查找统一的 `src/backend/appsettings.Development.local.json`，因此 Identity、SystemData、ReferenceData 和 UnifiedHost 应读取同一份私有配置。不得在各服务项目下再放一份同名配置形成第二配置源。

如需测试专用路径，可通过 `IndustrialPlatform:LocalConfigurationPath` 指定；相对路径以宿主 `ContentRootPath` 为基准，正常开发不应设置该值。

### 实际加载优先级

正常宿主先由 `WebApplication.CreateBuilder` 加载标准 ASP.NET Core 配置，再追加本地私有 JSON，最后写入由该文件计算出的基础设施覆盖项：

1. 已提交的 `appsettings.json`；
2. 已提交的 `appsettings.{Environment}.json`；
3. 标准环境变量、命令行等 ASP.NET Core 配置提供程序；
4. `src/backend/appsettings.Development.local.json`；
5. 根据 `RemoteDevelopment` 和 `DatabaseTopology` 生成的 `SqlSugar`、Redis、RabbitMQ、Seq 内存配置。

因此：

- 数据库拓扑和远程开发参数应统一写入本地私有 JSON，不要同时在多个来源重复配置。
- `IndustrialPlatform:DevelopmentInfrastructureMode` 和 `IndustrialPlatform:LocalConfigurationPath` 在加载本地文件之前读取，适合作为启动参数或环境变量使用。
- 环境变量使用 .NET 的双下划线写法，例如 `IndustrialPlatform__DevelopmentInfrastructureMode=Sqlite`。
- 不要依赖环境变量覆盖本地 JSON 内同名的 `DatabaseTopology` 字段；本地 JSON 是 Development 远程基础设施的最后权威输入。

## 3. 字段和值说明

### 3.1 启动选择字段

| 配置键 | 可用值 | 含义 |
| --- | --- | --- |
| `IndustrialPlatform:DevelopmentInfrastructureMode` | `Unified`、`Sqlite` | `Unified` 表示从统一私有文件生成 PostgreSQL/Redis 等配置；不是指 UnifiedHost。`Sqlite` 表示跳过远程私有配置，供本地隔离测试使用。未设置时按 `Unified` 路径处理。 |
| `IndustrialPlatform:LocalConfigurationPath` | 文件路径 | 测试或特殊启动时覆盖私有配置路径。正常开发留空。 |

使用本地 SQLite 时必须显式设置 `IndustrialPlatform__DevelopmentInfrastructureMode=Sqlite`，不要依赖“文件缺失”或 `RemoteDevelopment.Enabled=false` 作为隐式回退。SQLite 测试还必须验证 `SqlSugar:ConnectionString` 与 `DatabaseTopology:SharedSqliteFile` 指向同一预期文件。

### 3.2 `RemoteDevelopment`

| 字段 | 类型/示例 | 含义与规则 |
| --- | --- | --- |
| `Enabled` | `true` / `false` | `true` 才启用统一远程 PostgreSQL/Redis 配置。正常远程开发设为 `true`；SQLite 应使用上面的显式启动模式。 |
| `Host` | `db.internal` 或 Tailnet IP | PostgreSQL、Redis、RabbitMQ、Seq 共用的主机名/IP，不带协议和端口。 |
| `PostgreSql.Port` | `5432` | PostgreSQL 端口，范围 `1..65535`。 |
| `PostgreSql.UserName` | 占位值 | 开发数据库账号。不得写入模板之外的已提交文件。 |
| `PostgreSql.Password` | 占位值 | 开发数据库密码。不得输出或提交。 |
| `Redis.Port` | `6379` | Redis 端口。 |
| `Redis.Password` | 占位值 | Redis 密码。 |
| `Redis.DefaultDatabase` | `0` | Redis 逻辑数据库编号；缓存不是业务权威数据。 |
| `RabbitMq.Enabled` | `true` / `false` | 是否覆盖并启用远程 RabbitMQ 连接参数。 |
| `RabbitMq.Port` | `5672` | AMQP 端口。 |
| `RabbitMq.UserName` / `Password` | 占位值 | RabbitMQ 凭据。 |
| `RabbitMq.VirtualHost` | `/` 或专用 vhost | RabbitMQ Virtual Host。 |
| `Seq.Enabled` | `true` / `false` | 是否启用远程 Seq。 |
| `Seq.Scheme` | `http` / `https` | Seq URL 协议。 |
| `Seq.Port` | `5341` | Seq 服务端口。 |
| `Seq.ApiKey` | 空或私有值 | Seq API Key；禁入库、禁输出。 |

### 3.3 `DatabaseTopology`

| 字段 | 可用值/示例 | 含义与规则 |
| --- | --- | --- |
| `EnvironmentName` | `Development` | 拓扑声明所属环境。`Shared` 必须是精确的 `Development`；运行时初始化还会以实际宿主环境交叉校验。 |
| `Mode` | `Shared`、`PerService` | `Shared` 为单物理库；`PerService` 为按服务分物理库。其他值必须失败。 |
| `SharedDatabaseName` | `industrial_platform_dev` | `Shared + PostgreSQL` 的唯一物理库名，必填。所有服务应解析为同一值。 |
| `SharedSqliteFile` | `industrial-platform.db` | `Shared + SQLite` 的唯一物理文件，使用 SQLite 时必填。 |
| `ServiceDatabases` | `{ "identity": "identity_dev" }` | `PerService` 下稳定服务键到物理库名的显式映射。`Shared` 下应为空。 |

当前稳定服务键必须使用代码中的小写形式：

- `identity`
- `systemdata`
- `referencedata`
- `unifiedhost`（仅 UnifiedHost 单连接入口）

键名按稳定标识处理，新增服务不得使用显示名称、中文名或随意改变大小写。ReferenceData 的 Dictionary、Parameter、DynamicProperty、Metadata、CodingRule、StateMachine、UnitOfMeasure 是同一服务内的七个逻辑模块，不得在 `ServiceDatabases` 中各建一项。

以后新增服务时，将它的稳定小写 `serviceKey` 加入同一映射体系；不能因为本文当前只列出三个业务服务，就复制一套连接解析、初始化或 Docker 规则。

## 4. Shared（单库）配置

适用于日常 Development。以下仅为脱敏结构示例：

```json
{
  "RemoteDevelopment": {
    "Enabled": true,
    "Host": "YOUR_PRIVATE_HOST",
    "PostgreSql": {
      "Port": 5432,
      "UserName": "YOUR_DB_USER",
      "Password": "YOUR_DB_PASSWORD"
    },
    "Redis": {
      "Port": 6379,
      "Password": "YOUR_REDIS_PASSWORD",
      "DefaultDatabase": 0
    },
    "RabbitMq": {
      "Enabled": false,
      "Port": 5672,
      "UserName": "YOUR_RABBIT_USER",
      "Password": "YOUR_RABBIT_PASSWORD",
      "VirtualHost": "/"
    },
    "Seq": {
      "Enabled": false,
      "Scheme": "http",
      "Port": 5341,
      "ApiKey": ""
    }
  },
  "DatabaseTopology": {
    "EnvironmentName": "Development",
    "Mode": "Shared",
    "SharedDatabaseName": "industrial_platform_dev",
    "SharedSqliteFile": "industrial-platform.db",
    "ServiceDatabases": {}
  }
}
```

预期结果：

- Identity、SystemData、ReferenceData 独立 Host 均连接 `industrial_platform_dev`。
- UnifiedHost 也只建立指向该共享库的一套连接。
- ReferenceData 仍只使用自己的 `reference_data` Schema、表前缀、迁移账本和 Outbox；七个模块不拆七个物理库。
- 任何代码都不得因为逻辑身份 `referencedata_db` 或服务路径 `reference-data` 再创建同名物理库。

### 云端 Docker 必须同步

`appsettings.Development.local.json` 不会自动修改云服务器上的 `deploy/cloud-dev/.env`。Shared 模式下，Docker 初始化涉及的数据库变量必须全部指向同一个 `SharedDatabaseName`：

```dotenv
DATABASE_TOPOLOGY_MODE=Shared
SHARED_DATABASE_NAME=industrial_platform_dev
POSTGRES_DB=industrial_platform_dev
IDENTITY_DATABASE=industrial_platform_dev
SYSTEMDATA_DATABASE=industrial_platform_dev
REFERENCE_DATA_DATABASE=industrial_platform_dev
UNIFIEDHOST_DATABASE=industrial_platform_dev
```

初始化脚本即使多次收到同名目标，也只能幂等确认同一数据库存在，不能创建 `identity_db`、`reference-data`、`referencedata_db` 等额外物理库。备份脚本也应对相同目标去重，避免同一库被重复备份成多个文件。

## 5. PerService（多库）配置

真正按服务分库时应运行独立 API Host，并为每个已启动服务显式配置物理库：

```json
{
  "RemoteDevelopment": {
    "Enabled": true,
    "Host": "YOUR_PRIVATE_HOST",
    "PostgreSql": {
      "Port": 5432,
      "UserName": "YOUR_DB_USER",
      "Password": "YOUR_DB_PASSWORD"
    },
    "Redis": {
      "Port": 6379,
      "Password": "YOUR_REDIS_PASSWORD",
      "DefaultDatabase": 0
    },
    "RabbitMq": { "Enabled": false },
    "Seq": { "Enabled": false }
  },
  "DatabaseTopology": {
    "EnvironmentName": "Development",
    "Mode": "PerService",
    "SharedDatabaseName": null,
    "SharedSqliteFile": null,
    "ServiceDatabases": {
      "identity": "identity_dev",
      "systemdata": "systemdata_dev",
      "referencedata": "referencedata_dev"
    }
  }
}
```

预期结果：

- Identity 只连接 `identity_dev`。
- SystemData 只连接 `systemdata_dev`。
- ReferenceData 只连接 `referencedata_dev`。
- 任一当前宿主映射缺失时启动失败，不使用逻辑名兜底。
- Docker 必须预创建或由受控编排显式创建这些完全一致的物理库；变量值不得与 `ServiceDatabases` 分叉。

### UnifiedHost 的限制

当前 UnifiedHost 使用一套 `SqlSugar` 连接组合多个模块。`PerService` 下启动 UnifiedHost 必须提供 `ServiceDatabases["unifiedhost"]`，但该映射只代表组合宿主的一套物理连接，并不等于 Identity、SystemData、ReferenceData 已实现真正分库。

因此：

- 需要真正多库验收时，使用独立服务 Host，不使用 UnifiedHost 证明分库成功。
- 不得为了让 UnifiedHost 启动而把三个服务映射到同一库后宣称 `PerService` 已通过。
- 若未来要求 UnifiedHost 同时连接多个物理库，必须先设计每模块独立连接注册与迁移协调，不能在普通功能中顺手改造。

## 6. 未来新服务的完整接入方式

当前只有 Identity、SystemData、ReferenceData 接入这套基础设施。以后新增 MasterData、OperationalData 或其他服务时，必须一次性完成“拓扑配置、服务初始化、种子、Docker、备份、readiness、测试”整条链路，不能只让 API 连上数据库。

### 6.1 先声明稳定身份和数据边界

新增服务在写配置前先明确以下稳定信息：

| 项目 | 示例形式 | 规则 |
| --- | --- | --- |
| `serviceKey` | `newservice` | 全平台唯一、全小写、创建后不随项目名或显示名变化。 |
| 逻辑数据库名 | `newservice_db` | 表示服务的数据所有权；Shared 下仍保留，但不是物理库名。 |
| PostgreSQL Schema | `new_service` | Shared 下隔离对象命名；不得使用其他服务的 Schema。 |
| 表前缀 | `new_service_*` | 避免共享物理库中的命名碰撞。 |
| Migration Ledger | 服务 Schema 内的 `schema_migrations` | 每个服务一套，不因 Shared 合并成平台总账本。 |
| Seed Ledger | 服务 Schema 内的 `seed_ledger` | 记录稳定 SeedKey、版本、Checksum 和执行结果。 |
| Outbox | 服务级 | 只有服务发布集成事件时使用；逻辑子模块不机械复制。 |

如果新增的是现有服务内部的逻辑模块，它复用所属服务的上述身份、连接和账本，不进入 `DevelopmentService` 或 `ServiceDatabases`，也不增加 Docker 数据库变量。

### 6.2 应用配置接线

新增独立服务 Host 时至少完成以下接线：

1. 在 `DevelopmentInfrastructureConfiguration` 中登记新的 `DevelopmentService` 枚举值，以及唯一的 `(serviceKey, logicalDatabaseName)` 映射。
2. 在新 Host 的 `Program.cs` 中调用 `AddOptionalLocalDevelopmentInfrastructure(DevelopmentService.<NewService>)`，且必须发生在数据库、缓存、消息总线等服务注册之前。
3. 在该 Host 的 `appsettings.Development.json` 提供安全的本地默认值和完整 `DatabaseTopology` 结构；私有主机与凭据仍只进入统一的 `appsettings.Development.local.json`。
4. `Shared` 下不向 `ServiceDatabases` 增加无效映射；新服务直接解析 `SharedDatabaseName`。
5. `PerService` 下向 `ServiceDatabases` 增加精确的小写服务键，例如：

```json
{
  "DatabaseTopology": {
    "EnvironmentName": "Development",
    "Mode": "PerService",
    "SharedDatabaseName": null,
    "SharedSqliteFile": null,
    "ServiceDatabases": {
      "identity": "identity_dev",
      "systemdata": "systemdata_dev",
      "referencedata": "referencedata_dev",
      "newservice": "newservice_dev"
    }
  }
}
```

6. 向 SystemData 注册同一个 `serviceKey`、逻辑数据库名、Provider、目标版本、Migration/Seed 产物和 Owner；SystemData 只能根据 `DatabaseTopology` 得到物理目标，注册请求不得携带任意连接串。
7. 按下一节分别接入 UnifiedHost 和 Gateway。两种部署方式共享服务实现，但不能互相串联，也不能另写数据库解析规则。

### 6.3 UnifiedHost 与 Gateway 两种入口

UnifiedHost 和 Gateway 是并列的外部入口：

- UnifiedHost 在一个进程内组合服务模块，适合当前默认部署。
- Gateway 只代理多个独立 API Host，适合分布式边界验证和未来拆分。
- Gateway 不代理 UnifiedHost，UnifiedHost 也不嵌入 Gateway。一次运行选择一种入口，外部 URL 前缀应保持一致。

#### UnifiedHost 接入契约

进入 UnifiedHost 的服务必须在自己的 API 项目提供 `IUnifiedHostModule` 实现，并完整实现：

| 成员 | 要求 |
| --- | --- |
| `ServiceKey` | 与数据库拓扑、初始化器、SystemData 注册使用同一个稳定小写服务键。 |
| `ExternalPathPrefix` | 与 Gateway 的 `PathPrefix` 一致，例如外部前缀，例如 `/newservice`。 |
| `RegisterServices` | 调用服务已有的 `Add<NewService>Module`，不得在适配器中复制业务注册。 |
| `RegisterHealthChecks` | 注册带服务前缀的 readiness/capability 检查，避免与其他模块重名。 |
| `MapEndpoints` | 复用独立 Host 的端点映射，不维护第二套 Controller 或路由。 |

还必须：

- 将适配器显式加入 `UnifiedHostModuleCatalog.Modules`；目录顺序同时表达注册和初始化前置关系，禁止程序集自动扫描。
- 注册同 `ServiceKey` 的 `IServiceInitializer`。迁移协调器找不到初始化器时必须启动失败。
- 由 `ModuleMigrationCoordinatorHostedService` 按目录顺序执行服务自己的 `Inspect → Plan → Apply → Verify`，不得在 UnifiedHost 复制具体 Migration/Seed。
- 更新 UnifiedHost 项目引用、认证授权适配、前缀剥离、健康聚合及测试；共享认证不代表绕过服务权限。
- 至少用一个真实业务端点验证 `/<prefix>/api/v1/**` 已映射，不能只验证未知地址返回 404。

#### Gateway 接入契约

当前 Gateway 不需要、也没有 `IGatewayModule`。它的显式接入契约是 `Gateway:Services[]`；没有新的复杂需求时不要再造平行接口或自动发现机制。

每个独立下游配置包含：

```json
{
  "Name": "newservice",
  "PathPrefix": "/newservice",
  "DestinationUrl": "http://localhost:6001"
}
```

字段规则：

- `Name` 必须等于稳定 `serviceKey`，并在列表内唯一。
- `PathPrefix` 必须以 `/` 开头、在列表内唯一，并与 `IUnifiedHostModule.ExternalPathPrefix` 保持一致。
- `DestinationUrl` 必须是独立 API Host 的内部绝对地址；不得指向 Gateway 自身、UnifiedHost、公网临时地址或前端地址，也不得包含凭据。
- 下游必须提供 `/health/live` 和 `/health/ready`；Gateway 自动将已配置下游的 `/health/ready` 纳入聚合。
- `GatewayRouteFactory` 负责生成 YARP route/cluster 并剥离 `PathPrefix`，业务 Controller 不增加 Gateway 专用前缀。
- 认证授权、Migration、Seed、数据库连接和业务错误仍由下游服务负责；Gateway 只处理 CORS、代理、超时、下游健康和代理错误信封。

新增 Gateway 下游时必须同步：

1. 更新 Gateway 各环境的 `Gateway:Services[]` 或部署环境覆盖值。
2. 更新 `deploy/scripts/dev.ps1 -IndependentServices` 的服务注册表和端口，确保它会启动所有已配置下游；不能让 Gateway readiness 永久指向未启动服务。
3. 更新 `deploy/scripts/smoke.ps1 -IndependentServices`，同时探测下游直连 health 和 `Gateway /<prefix>/health`，并校验转发响应中的服务身份。
4. 更新 `GatewayBoundary` 的禁止业务程序集清单或等价架构约束，保证 Gateway 没有引用新服务的 Domain/Application/Infrastructure/API。
5. 更新配置绑定、前缀剥离、真实代理、下游不可达 503、超时 504、readiness 聚合和 CORS 测试。
6. 前端分布式验证只连接 Gateway；不能通过直连下游或 Mock 证明 Gateway 模式已通过。

#### 两种入口的共同验收

- 同一个外部业务 URL 在 UnifiedHost 和 Gateway 模式下具有相同路径、认证、权限与响应契约。
- UnifiedHost 模式用真实模块端点证明进程内映射；Gateway 模式用真实下游证明网络转发，不能只测通用 Stub。
- 两种模式都要验证服务 readiness；Gateway 自身 liveness 成功不代表下游服务已就绪。
- 同一验收过程中不要同时占用相同端口启动两套入口。优先复用现有调试环境，隔离验证使用任务自有端口。

### 6.4 Migration 与种子接入

Docker 只负责准备 PostgreSQL 实例、物理数据库及必要角色，不负责插入业务种子。Seed 必须由服务自己的版本化初始化器管理。

新服务必须：

- 实现并注册服务级 `IServiceInitializer`，保持 `Inspect → Plan → Apply → Verify` 契约。
- Migration 只创建本服务 Schema、表、索引、约束和服务级 Ledger，不使用 `EnsureCreated`、删除重建或启动时无版本 DDL。
- 每组种子使用稳定的 `SeedKey + SeedVersion + Checksum` 写入本服务 Seed Ledger；重复启动不得重复插入或覆盖用户修改。
- 需要升级默认数据时新增版本并定义兼容升级行为，不能修改已执行版本的内容后继续沿用旧 Checksum。
- 种子中的稳定 ID、代码、权限、菜单和默认配置必须确定且可重复；环境相关地址、密码、连接串和演示数据不得成为平台基础种子。
- Shared 下各服务仍各自执行 Migration/Seed，并由 UnifiedHost 或 SystemData 按确定顺序串行协调同一物理库的 DDL；不能把三个现有服务和新服务合成一套大迁移。
- PerService 下初始化器、实际连接、Ledger 和 readiness 必须全部指向该服务映射的物理库。
- 首次初始化、重复初始化、升级初始化和失败重试都必须有测试；部分失败不能写成成功，也不能让其他服务的 readiness 代替本服务。

如果新服务带有默认菜单、权限或系统资源，还必须同步更新其权威种子、SystemData 预览/导入资源清单和前端运行时映射，并验证“全新数据库自动出现、已有数据库可预览后幂等导入、用户自定义不被覆盖”。不能只在前端静态写菜单。

### 6.5 云端 Docker 接入

Docker Compose 不读取 `appsettings.Development.local.json`。新增服务时必须同步检查以下文件：

- `deploy/cloud-dev/.env.example`：增加脱敏的数据库变量示例；
- 云服务器私有 `deploy/cloud-dev/.env`：部署人员设置实际值，不提交；
- `deploy/cloud-dev/compose.yaml`：把变量显式传给 PostgreSQL 容器；
- `deploy/cloud-dev/postgres/init-databases.sh`：幂等准备允许的物理目标；
- `deploy/cloud-dev/backup-postgres.sh`：备份新增的唯一物理目标并按数据库名去重；
- `deploy/cloud-dev/README.md`：同步 Shared/PerService 操作说明和恢复清单。

变量命名使用稳定的大写服务键，例如 `NEWSERVICE_DATABASE`。它的值必须与应用拓扑对齐：

```dotenv
# Shared：所有服务变量都等于 SharedDatabaseName，不新增物理库
DATABASE_TOPOLOGY_MODE=Shared
SHARED_DATABASE_NAME=industrial_platform_dev
POSTGRES_DB=industrial_platform_dev
IDENTITY_DATABASE=industrial_platform_dev
SYSTEMDATA_DATABASE=industrial_platform_dev
REFERENCE_DATA_DATABASE=industrial_platform_dev
UNIFIEDHOST_DATABASE=industrial_platform_dev
NEWSERVICE_DATABASE=industrial_platform_dev
```

```dotenv
# PerService：每个值与 ServiceDatabases 中的映射逐项一致
POSTGRES_DB=systemdata_dev
IDENTITY_DATABASE=identity_dev
REFERENCE_DATA_DATABASE=referencedata_dev
NEWSERVICE_DATABASE=newservice_dev
```

注意：

- 增加环境变量不等于允许无条件建库。Shared 下重复的同名目标只能被幂等确认一次；备份也只能生成一次。
- PerService 下才允许创建新服务独立物理库；缺少变量、空值、非法库名或与 `ServiceDatabases` 不一致必须失败。
- PostgreSQL 官方 entrypoint 的初始化脚本通常只在全新数据卷首次创建集群时执行。对已有数据卷增加服务数据库，必须走受控、可审计的显式 provision 流程，不能删除数据卷来触发脚本。
- Docker 初始化不得执行服务业务 Migration 或 Seed；应用初始化器仍是唯一入口。
- 删除服务、改库名或切换拓扑时，Docker 脚本不得自动 DROP 旧库。先备份、报告 drift，再单独审批迁移和清理。

### 6.6 新服务完成标准

新服务只有同时满足以下条件才算完成接入：

1. Shared 下，它与所有现有服务命中同一物理库，但仅操作自己的 Schema、表和 Ledger。
2. PerService 下，它命中显式映射的独立物理库；缺少映射时启动失败。
3. SystemData 注册目标、应用实际连接、Migration/Seed 执行目标和 readiness 身份完全一致。
4. 全新环境能初始化到 Ready；第二次启动零重复 Seed；升级和失败重试保持 Ledger 一致。
5. Shared Docker 最终只存在一个预期业务物理库；PerService Docker 只存在清单声明的物理库。
6. 备份清单覆盖全部唯一目标，重复物理库不重复导出；恢复说明与拓扑一致。
7. 日志、测试证据和错误消息均不泄露凭据或完整连接串。
8. 独立 Host 和计划支持的 UnifiedHost/Gateway 入口均按部署边界完成验证。

## 7. 新服务或新模块接入清单（强制）

每次新增有持久化能力的服务或初始化单元，开发任务必须完成以下检查；逻辑模块复用所属服务配置，不单独接入数据库拓扑。

### 配置与代码

- [ ] 定义唯一、稳定、小写的 `serviceKey` 和逻辑数据库名。
- [ ] 将宿主接入 `AddOptionalLocalDevelopmentInfrastructure`，复用公共 `DatabaseTopologyResolver`。
- [ ] 禁止在服务代码、Migration、Docker 脚本中自行拼接物理数据库名。
- [ ] `Shared` 使用 `SharedDatabaseName`/`SharedSqliteFile`；`PerService` 只使用显式 `ServiceDatabases[serviceKey]`。
- [ ] 初始化、readiness、SystemData 注册和实际 `SqlSugar` 连接使用同一个解析结果。
- [ ] Shared 只共享物理容器，不共享表所有权、Repository、Schema、Ledger 或跨服务外键。
- [ ] 更新 `appsettings.Development.local.example.json` 的结构说明，但不得加入真实凭据。
- [ ] 更新 Docker 初始化与备份清单；Shared 去重，PerService 与映射逐项一致。

### 自动化验证

- [ ] `Development + Shared + PostgreSQL`：所有相关服务解析到同一个物理库。
- [ ] `Development + PerService + PostgreSQL`：每个独立 Host 解析到自己的显式映射。
- [ ] Shared 缺少 `SharedDatabaseName`：启动失败。
- [ ] PerService 缺少当前服务映射：启动失败。
- [ ] 非法 `Mode`：启动失败。
- [ ] `Test`、`Staging`、`Production + Shared`：校验失败。
- [ ] 配置文件自动发现与显式路径覆盖行为有测试。
- [ ] 实际连接目标、初始化目标、Migration/Seed Ledger 和 readiness 的目标身份一致。
- [ ] Docker 首次初始化和重复执行幂等，Shared 不产生服务名物理库。
- [ ] 日志、异常、审计和测试输出不包含密码或完整连接字符串。
- [ ] 拓扑切换不会隐式复制、删除或覆盖既有数据。

### 验收证据

开发完成不能只提供“服务启动成功”。至少应保留以下脱敏证据：

1. 各宿主解析出的 `EnvironmentName`、`Mode`、`ServiceKey`、逻辑数据库名和物理数据库名；
2. Shared 下物理库去重结果，PerService 下服务到物理库的一一映射；
3. Migration/Seed Ledger 与 readiness 使用同一目标的测试结果；
4. Docker 初始化脚本在两种拓扑下的静态测试或隔离环境验证；
5. 未泄露凭据、未操作非目标数据库的确认。

## 8. 常见错误

| 错误做法 | 正确做法 |
| --- | --- |
| 在 ReferenceData 中写死 `referencedata_db` 作为连接库 | 保留它作为逻辑身份，物理目标交给 `DatabaseTopologyResolver` |
| Shared 模式下 Docker 仍创建 `reference-data` | 所有 Docker 数据库变量对齐 `SharedDatabaseName`，并对初始化/备份去重 |
| 给 ReferenceData 七个模块分别建库 | 七个模块共用 ReferenceData 服务级数据库边界和基础设施 |
| PerService 缺映射时退回逻辑库名 | 启动失败并指出缺少的稳定服务键 |
| 用 UnifiedHost 单连接证明多库可用 | 使用独立 Host 验证真正 PerService |
| 修改 `Mode` 后自动搬数据或删旧库 | 先报告 drift，再走单独审批的数据迁移方案 |
| 在故障信息中打印完整连接串 | 只输出环境、模式、服务键和脱敏物理目标 |
| 新功能只跑默认 Shared 测试 | Shared 与 PerService 都必须覆盖，并核对初始化/readiness |
| 把业务 Seed 写进 Docker init 脚本 | Docker 只 provision 物理目标，Seed 由服务 `IServiceInitializer` 和 Seed Ledger 管理 |
| 新增服务只改 `ServiceDatabases` | 同步接入公共解析器、SystemData、Migration/Seed、Docker、备份、readiness 和测试 |
